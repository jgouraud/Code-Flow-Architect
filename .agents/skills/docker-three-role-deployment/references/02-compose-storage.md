# DOCKER.COMPOSE — services, networks and durable state

- **DOCKER.COMPOSE1 M** Distinguish `ports` (host-published interface) from `expose` (documentation/container-port) and Docker network membership. Only the trusted gateway should be host-published in the protected-app pattern. If ingress arrives on another host, publish *only* on an approved private interface with firewall restrictions, not `0.0.0.0` by default.
- **DOCKER.COMPOSE2 M** Use stable Compose service names (`frontend:8080`, `auth:4180`) on declared shared networks; preserve isolation between gateway and updater, and between external ingress and private app resources.
- **DOCKER.COMPOSE3 M** Persist durable data in named volumes, external storage or an explicitly owned bind mount; no authoritative data stored only in container writable layers. Document ownership, permissions, backup/restore, update consistency and rebuild expectations.
- **DOCKER.COMPOSE4 M** For an update worker sharing data with an app, mount app data read-only where feasible; restrict updater writes to the intended data area. Ensure the app never observes a half-written version: stage + validate + atomically switch/version where storage semantics support it. Synchronize readers for platforms with different atomicity guarantees.
- **DOCKER.COMPOSE5 M** Define update job lifecycle and concurrency control. A job must be safe after crash/retry; prevent two updater processes from simultaneously publishing conflicting versions. A Compose profile is an opt-in launch mechanism, **not** a scheduler or mutex.
- **DOCKER.COMPOSE6 M** Keep secrets out of image layers, Git, debug logs, templated Nginx config, and committed `.env` files. Use a supported secrets manager or appropriately protected file mounts; Compose local file secrets are not an encrypted vault.
- **DOCKER.COMPOSE7 S** Prefer pinned/approved images, multi-stage builds when useful, non-root runtime, minimal capabilities, readonly filesystem and bounded resource usage where compatible with actual workload.
- **DOCKER.COMPOSE8 M** Validate with `docker compose config -q` before changes, then investigate actual runtime reachability/health. `depends_on: service_started` does not prove readiness; `service_healthy` only gates startup and is not automatic self-healing.
- **DOCKER.COMPOSE9 M** Keep developer live-code bind mounts, debug ports, hot reload, privileged tooling, Docker daemon access and wide egress out of normal production profile unless specifically approved.
- **DOCKER.COMPOSE10 M** Do not use `docker compose down -v`, broad volume prune or `docker system prune --volumes` as a normal deploy or transient-failure remedy. Inspect context and backups before destruction.
- **DOCKER.COMPOSE11 S** When the app genuinely requires outbound service access, supply a deliberate egress path; an `internal: true` network prevents default external routing and cannot be applied blindly to an OIDC client that must reach its IdP.

**Template caveat:** `templates/compose.three-role.yaml` contains obvious project placeholders, an example OIDC configuration and local-only ingress. It is not evidence that a target deployment is ready. Update the public DNS, paths, image references, update command, host bind policy, credentials and readiness checks before launching.
