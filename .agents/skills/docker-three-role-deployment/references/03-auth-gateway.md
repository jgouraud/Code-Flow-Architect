# DOCKER.AUTH — gateway, auth subrequest and OIDC boundary

Typical flow: browser -> corporate TLS ingress -> Nginx -> `auth_request /oauth2/auth` -> OAuth2 Proxy -> OIDC identity. Successful 2xx authorization permits upstream; 401 begins browser sign-in; 403 denies; 5xx must not be converted into permitted access. Nginx `auth_request` must be present in the deployed Nginx build.

- **DOCKER.AUTH1 M** Make the externally reachable gateway the *only* app ingress. Test that reaching the app port directly is impossible from an untrusted host and not accidentally exposed by another Compose service, host-network binding, VPN route or load balancer.
- **DOCKER.AUTH2 M** Authenticate each protected HTTP path, including websocket upgrades if used. Do not accidentally exempt static endpoints containing private information, API routes, uploads, downloads, previews, health/debug or redirect handlers.
- **DOCKER.AUTH3 M** Trust forwarded Host/Proto/IP/User headers only from explicitly trusted and sanitizing upstream proxies. Remove or overwrite client-supplied identity headers at the trust boundary; never treat `X-Forwarded-*` received from arbitrary clients as authoritative.
- **DOCKER.AUTH4 M** Configure OIDC issuer, client identity, redirect URI, session cookie domain/security, trusted proxy chain, and IdP eligibility policy explicitly. `email_domains=*` is **not** an adequate definition of who is authorized to use a private application.
- **DOCKER.AUTH5 M** Restrict OIDC redirect and `rd`/return destinations to approved origin(s); disallow open redirects, hostile host headers and callback URL manipulation. Set cookie Secure/HttpOnly/SameSite appropriately for the actual HTTPS entrypoint and login flow.
- **DOCKER.AUTH6 M** Define permission-denied (403), unauthenticated (401), auth upstream unavailable (5xx), expired/revoked session, and logout behavior separately. Errors in the auth path must fail closed; do not expose the frontend because the IdP is down.
- **DOCKER.AUTH7 M** Prevent request-header spoofing: only pass verified identity headers (e.g. `X-Auth-Request-User`) from the auth subrequest, never forward client-supplied replicas as verified identities. The upstream must not be directly reachable by clients who can set those headers.
- **DOCKER.AUTH8 M** Configure downstream proxying for real requirements: websocket upgrade, streamed uploads, body limits, read/write timeouts, large cookies, multiple `Set-Cookie` headers, request IDs, and forwarded identity. Do not copy enormous timeouts/100-MB bodies without use-case evidence.
- **DOCKER.AUTH9 M** With upstream TLS termination, verify how HTTPS scheme and external host are propagated. A constant trusted scheme (`https`) may be appropriate if the gateway is reachable only through an HTTPS-terminating trusted proxy; otherwise use a validated allowlisted trust chain, never a blind fallback from a raw `X-Forwarded-Proto` header.
- **DOCKER.AUTH10 S** Prefer maintained Nginx and OAuth2 Proxy releases and vendor documentation, especially for session refresh/multiple cookies/Entra group-claim semantics. Check installed versions and behavioral tests rather than assuming a config copied from a tutorial works unchanged.

**Deployment test matrix:** unauthenticated browser -> sign-in, authenticated+authorized -> frontend, authenticated+unauthorized -> denial, auth unavailable -> deny, direct backend-port attempt -> refused, altered Host/Proto/X-Auth-Request-User -> cannot escalate, cookie expiry/logout -> reauthenticate, API unauthorized -> expected 401/403 (not HTML login response if machine API).

Sources: supplied `nginx.conf` / `docker-compose.yml`; Nginx `auth_request` documentation (https://nginx.org/en/docs/http/ngx_http_auth_request_module.html); OAuth2 Proxy Nginx integration (https://oauth2-proxy.github.io/oauth2-proxy/configuration/integrations/nginx/) and option reference (https://oauth2-proxy.github.io/oauth2-proxy/7.12.x/configuration/overview/). Verify current versions before use.
